# Building the UI

This document says how the screens in [design-reference.md](design-reference.md) are built in SwiftUI: where views and state live, how each component is made from the system's parts, what each phase of [workplan.md](workplan.md) adds, and the sample data that makes a preview match the renders. It is written for an engineer, or a session, that has the design and the plan and is about to open Xcode.

## Shape of the code

The app keeps its layers as they are: `Nageire/Session` holds `AppModel` and the GitHub session, `Nageire/Notes` holds the library, the outbox, and the file format, and `Nageire/Views` holds the screens. The redesign adds one folder and fills the views folder:

- `Nageire/Design/Tokens.swift`: the semantic names (`.surfaceCard`, `.textSecondary`, `.textDerived`, `.textMark`) on top of the color sets of the Asset Catalog, the spacing constants (`Spacing.gutter`, `.rowPadding`, `.rowGap`, `.control`, `.controlCompact`), and the radii (`Radius.input`, `.thumbnail`, `.card`, `.sheet`). The token names themselves (`.paper`, `.paperRaised`, `.paperSunken`, `.hairline`, `.ink`, `.ink2`, `.inkFaint`, `.accentText`, `.accentWash`, `.onAccent`) are not written anywhere: Xcode generates them from the catalog. The accent is `.tint`.
- `Nageire/Design/Typography.swift`: the note body style with its leading, the scaled heading sizes, the derived style, and the device-code style.
- `Nageire/Design/Styles.swift`: `PrimaryButtonStyle`, `SecondaryButtonStyle`, and `TextButtonStyle`, the `Hairline` rule, the `View` extension for a hairline border, and the `ShapeStyle` extension for a fill that floats.
- `Nageire/Design/Components/`: one file per component of the design reference (`NoteRow`, `DayHeader`, `UnsentMark`, `DraftRow`, `RefusedBanner`, `UndoBar`, `EmptyState`, `NoteHeader`, `RelatedSection`, `StepList`, `DeviceCodeCard`, `AccessoryBar`), each with a `#Preview` on the sample data below.
- `Nageire/Views/`: the screens, one file each: `SignInView`, `RepositoryPickerView`, `StreamView`, `TossSheet`, `NoteView`, `SettingsView`, and on macOS `QuickEntryWindow`. `NoteEditor` is the editor the toss sheet and the note screen share, the SwiftUI face of the text view under `Nageire/Editor`; the button that saves belongs to the screen around it.
- `Nageire/Notes/DayGroup.swift`: the notes of one day, for a heading of the stream, with the label the heading shows. `NoteEntry` itself carries what a row shows of a note: the display title, the excerpt, and the attachment count.
- `Nageire/Editor/`: the TextKit 2 view (`MarkdownTextView`), the attributes its Markdown gets (`MarkdownStyler`), and the layout fragments that draw a task's box and an image's thumbnail. The line parser, `MarkdownLine`, is under `Nageire/Notes`, since the list reads the same markers for a row's title and excerpt.

A view never spells a color, a size, or a font that the design names; it uses the token. A view that needs a value the tokens lack is a sign that the design reference is missing something, and the reference is extended first.

## State

- `AppModel` stays the one observable object in the environment, and keeps the library, the outbox, the session, and the repository. The redesign adds to it what must outlive a screen: the pending deletion (the note, the time its undo window has left, and the task running the window, which is absent while the app is not in front) and, from phase 5, the on-device results cache.
- Screen state (the selection, whether the sheet is up, the search query, the open menu) stays in the screen's `@State`, as today.
- The draft of a new note stays in `UserDefaults` through `@AppStorage("draft")`, as today, so that it survives a relaunch.
- The undo window is a `Task` on `AppModel` that sleeps for the time left in the pending deletion, ten seconds at first, and queues the deletion when it wakes. When the scene leaves `.active`, which the root view reports from `scenePhase` as `isInFront`, the task is cancelled and the time left is kept in the pending deletion; when the scene is active again, a new task starts with that remainder. The window therefore never runs while the bar cannot be seen, and the bar stays up throughout. "取り消す" cancels the task and puts the note back. A second deletion and a sign-out queue the pending one at once, so that one bar stands for one note and nothing is lost with the account; choosing another repository undoes it instead, since the copy it was made among is dropped on the same line and a recorded deletion would be applied to the new repository. `UndoManager` from the environment, handed to `deleteNote`, registers the same undo so that Command-Z and the shake gesture reach it, and the registration is removed when the window closes. The model does not survive a relaunch within the window: the note is then back, as if undone.
- The size classes decide the layout as today: `NavigationSplitView` shows the list beside the note in a regular width and one column in a compact one, and a new note is a sheet in a compact width and the detail column otherwise.

## Tokens in code

- Colors are color sets in `Assets.xcassets` with an Any and a Dark appearance, named as the design reference lists them. `AccentColor` is the accent, which makes `.tint` and every system control follow it. Xcode generates a `ShapeStyle` name for each set (`ASSETCATALOG_COMPILER_GENERATE_SWIFT_ASSET_SYMBOL_EXTENSIONS`), so a set added to the catalog is a token in code with nothing else to write.
- The semantic names are computed properties over the token names, so that a later change of a token's role (say, the sidebar surface) is one line.
- The hairline is one physical pixel: `@Environment(\.pixelLength)`, drawn by `Hairline` as a `Rectangle` in `.hairline` and by `.hairlineBorder(_:)` as a stroke just inside a shape, or the list's own separator tinted with `.hairline` and inset to the gutter.
- The floating shadow belongs to the fill of what floats, not to the view: `.background(.tint.floating, in: .capsule)`. `floating` is a `ShapeStyle` extension that gives the fill two drop shadows in `.ink` at the opacities of the design reference, and in dark mode the black ones. A shadow on the view would be drawn again whenever anything inside it changed. SwiftUI's shadow radius is half the blur the stylesheet gives, so the two are 12 and 1.
- Type uses the system text styles, so Dynamic Type works without further work: `.largeTitle` bold, `.title2` bold, `.body`, `.subheadline`, `.footnote`, `.caption`. The note body is `.body` with `.lineHeight(.multiple(factor: 1.65))`, which keeps the line at 1.65 times the size at every text size, and the headings inside a note scale from 24, 20, and 17 with `@ScaledMetric(relativeTo: .body)` at a line height of 1.35. The derived style is `.body.weight(.semibold).italic()` in `.ink2`. The device code is `.system(size: 38, weight: .medium, design: .monospaced)` with a tracking of 0.14 of its size, scaled with `@ScaledMetric` as well.

## Components

- Buttons. `PrimaryButtonStyle` draws a capsule in `.tint.floating` with the label in `.onAccent` and `.body.weight(.semibold)`, 44 high with 20 of horizontal padding, and the vase symbol at the leading edge; a `compact` parameter gives 34 high, 14 of padding, and `.subheadline.weight(.semibold)`. `SecondaryButtonStyle` is the same capsule in `.paperRaised` with a hairline stroke and the label in `.ink`. `TextButtonStyle` is the label in `.accentText` with 12 of padding. Inside a system toolbar the button is left to the system: iOS 26 draws it as glass with the accent tint (`.glassProminent`), which is what the design shows in the bottom bar, so there the view sets only the label, which is the glyph. A keyboard hint beside a button on macOS is a `Text` in `.footnote` and `.ink2`, 10 away.
- The stream. A `List` in `.plain` style with a `DayHeader` row before the notes of each day and a `NoteRow` per note. The heading is a row and not a `Section` header, which iOS and macOS inset differently from the rows under it; it cannot be selected and reads as a header to VoiceOver. The rows take `EdgeInsets.stream`, the headings `EdgeInsets.streamHeader`, both with `Spacing.listGutter` at the sides, which is the gutter on iPhone and 16 in the sidebar on macOS. The separator is the list's, tinted `.hairline`. Pull to refresh stays. The row's title line uses `.body.weight(.semibold)` with `.lineLimit(1)`, the excerpt `.subheadline` in `.ink2` with `.lineLimit(2)`, and the meta line an `HStack` of 10 of spacing in `.footnote` and `.ink2`. A tentative title swaps the title's style for the derived one and adds an accessibility label that says it was suggested. The selected row on macOS is the list's selection tinted with `.accentWash`.
- The bottom bar on iPhone. `DefaultToolbarItem(kind: .search, placement: .bottomBar)`, `ToolbarSpacer(.flexible, placement: .bottomBar)`, and the toss button in a `ToolbarItem(placement: .bottomBar)`; the system wraps the field and the button in one glass group. The shape of the bar is the system's, not a custom view. The button is the vase alone, named "新しいメモ" for VoiceOver. While a draft waits in the sheet, `DraftRow` sits at the top of the stream, "書きかけ" over the first line of the text in `.ink2`, and opens the sheet when tapped. On macOS and iPad in a regular width, search stays in the sidebar through `.searchable(placement: .sidebar)` and the primary button is a toolbar item, as today.
- The undo bar. A `.safeAreaInset(edge: .bottom)` on the stream that shows `UndoBar` while `AppModel` holds a pending deletion, above the toolbar, with a transition of move and opacity. The bar is a capsule in `.paperRaised.floating`, the message in `.subheadline`, and the action in `TextButtonStyle`.
- The banner. `RefusedBanner` above the stream, in a top safe-area inset so that it shows over the empty state too, in `.accentWash` with `.accentText`; the card is a `Button` that opens Settings, the sheet on iOS and the window on macOS. It appears only while the outbox reports a refusal, never for a transient failure. A failed fetch shows nothing: the notes on the device stay listed.
- The toss sheet. A `.sheet` with `.presentationDragIndicator(.visible)` and the large detent, holding a `NavigationStack` whose toolbar carries the close button on the leading side, the timestamp as the principal item in `.footnote` and `.ink2`, and the compact primary "完了" on the trailing side with the Command-Return shortcut. The editor fills the rest. In a wide window the same screen is the detail column without the close button, and the toolbar's own new-note button steps aside while it shows. The accessory bar arrives with the editor in phase 2, attached on iOS with `.toolbar(placement: .keyboard)`, and its three attachment buttons act from phase 3 and are absent until then. Dismissing keeps the draft; tossing clears it after `saveNote` succeeds. The toss saves inside a spring of 480 ms, and the list inserts the new row with its own insertion inside that animation, which is the one animation the app owns; the 120 ms by which the design reference has the row wait for the sheet is left to the system.
- The note screen. One `ScrollView` with 20 of vertical spacing holding `NoteHeader`, the body, and `RelatedSection`. In phase 1 the body is the text in the note body style with the existing Edit button kept before Share; in phase 2 it becomes the editor and Edit, Save, and Cancel go. The toolbar holds Share, which shares the text, and a `Menu` with GitHub で開く and 削除 as a destructive role; the menu is the system's. GitHub で開く opens the note's page on the default branch (`blob/HEAD/<path>`) and is disabled while GitHub does not have the note as it is shown: a new note has no page there, and an edited one's page shows the text before the edit. The back button is the navigation stack's. On iPhone the bar has no title, since the first line of the text is the title; on macOS the title is the display title.
- The note header. A `.footnote` line in `.ink2` built from the written date, the edited date as 今日 or 昨日 with the time or else the date, and a checkmark symbol for sent or the unsent mark, and, when the note has no heading and the model proposed one, the title in the derived header style with a `TextButtonStyle` "見出しにする" that inserts the heading line through the outbox's edit path.
- The related section. A `VStack` with the label, a hairline, the rows as `NavigationLink`s to the other notes, and the footnote line. It returns `EmptyView` when the list is empty, so that a short note shows nothing.
- Settings. A `Form` in `.grouped` style on `.paper`, its rows on `.paperRaised`. Each group is a `Section` with the header text, and the footer text where the design has one. Rows are `LabeledContent` for a value, `Toggle` for a switch, `Picker` with `.segmented` style for the serif choice, a text button in `.accentText` for 今すぐ送信, and a destructive `Button` in `.accentText` for サインアウト. A row that opens something (the account, which opens the GitHub profile, and the repository, which opens the picker) is a `Button` in the plain style whose label is the `LabeledContent` with the chevron, since the form's own button style boxes a button on macOS. The on-device section is one `Toggle` with the sentence as its footer, and when the model is unavailable the toggle is replaced by the unavailable sentence as the footer alone. The time of the last send is kept by `AppModel` in the defaults, set whenever the outbox reports a sent note or change.
- Sign-in and the device code. `StepList` is a `Grid` as today's three steps are, with the filled circle drawn as a `Circle` in `.ink` and the number in `.paper`; the current step is the same and a later step a hairline circle with the text in `.ink2`. `DeviceCodeCard` is a `.paperRaised` card with the hairline stroke and the code in the device-code style, selectable. The buttons are a primary and a secondary across the width, 10 apart, and the two footnotes are `Text` in `.footnote` and `.ink2` with `.multilineTextAlignment(.center)`. The logo is the mark variant: the vase and flowers without the background square, at 132 points, as the image set `AppMark` made from `vase.svg` and `flowers.svg` under `Nageire/AppIcon.icon/Assets/`, since `AppLogo.imageset` carries the background. The code screen is pushed on the stack the root view supplies, so Back is the stack's own. Both screens spread over the height they are given and scroll at a text size where they do not fit.
- The empty state. `ContentUnavailableView` is kept for the structure, with the vase outline as its image, the title in `.title2`, and the two lines in `.subheadline` and `.ink2`. The outline is `VaseOutline`, a `Shape` stroked in `.ink2`, since the logo's vase is a filled form and the design draws a line.
- Icons. SF Symbols everywhere, with the names the design reference lists. The vase for the primary action is `VaseGlyph`: the logo's vase path as a template image set (`Vase`), drawn at 20 points, or 16 compact, through `@ScaledMetric` so that it follows the text size, and in the color of the text beside it. A symbol template would scale with the font on its own and could take symbol effects, and nothing in the design needs either, so the image set is the final form.
- macOS. The window is the same `NavigationSplitView` with `.navigationSplitViewColumnWidth(min: 260, ideal: 320, max: 480)` as today; the sidebar's background is `.paperSunken`, the selected row `.accentWash`, and the note column centers its content at 680 with `.frame(maxWidth: 680)`. The quick-entry panel in phase 4 is 560 by 340 and, if it stays a window of the app, a second `Window` scene opened by a menu bar item and a shortcut. Whether it is a separate process instead is open in ux-redesign.md, and a global shortcut that works while another app is in front needs an event monitor or a helper; both are decided together in phase 4.

## Platform differences

`#if os(macOS)` marks the few places that differ, as today: the search placement, the toolbar placements, the settings window, and the quick-entry panel. iPad follows the size class, not the platform. Nothing else forks.

## Accessibility and the two appearances

- Every icon-only button is made with the `Button(_:systemImage:)` form or carries `.accessibilityLabel`, so VoiceOver reads it.
- Decorative drawing, the vase outline and the logo, is `.accessibilityHidden(true)`.
- A tentative title is announced as a suggestion, and the related section's rows as links to notes.
- Every screen is previewed in both color schemes and at the largest accessibility size with `.environment(\.dynamicTypeSize, .accessibility5)`, and the bottom bar is checked at that size on a device.
- Contrast is the tokens' and is not retuned per view. A view that looks too faint uses the next token, never an opacity.

## Previews

Every component and screen has a `#Preview` on `SampleData`, a fixture under the app target's Preview Content folder, which the tests reach through `@testable import`, that mirrors the prototype's sample so that a preview can be set beside the render. Each file in the folder is wrapped in `#if DEBUG`, so a release build holds none of it. A debug build launched with the argument `-sampleData stream` runs on the same fixture (`SampleScene` names the others: `empty` is the account before its first note, `refused` the account with GitHub refusing its writes, `deleted` the account just after deleting a note, with the undo bar up for its ten seconds, `signedOut` the app before sign-in): it is signed in as the sample account, holds the sample notes in memory, keeps its settings in defaults of its own, reads no Keychain, and reaches no network, so a screen can be photographed without an account. GitHub answers there as it would while the device is offline, which keeps the unsent note unsent. The app that hosts the unit tests, and the app Xcode starts for a preview, start the same way but signed out and empty, so that neither acts as the person at the keyboard.

The times of the notes are counted back from the moment the fixture is asked, so that the first two days are today and yesterday on any day, and a test passes the moment it wants. ## The editor, for phase 2

- One `UIViewRepresentable` and one `NSViewRepresentable` over a TextKit 2 text view (`NSTextContentStorage`, `NSTextLayoutManager`) that holds the note's Markdown as its plain text. The string in the view is the string in the file; styling is attributes, never inserted or removed characters. The storage keeps the plain text with the body attributes alone, and the content storage's delegate hands the layout manager a styled copy of each paragraph as it is laid out (`textContentStorage(_:textParagraphWith:)`), so an edit restyles the paragraphs it touched and nothing is written back into the storage.
- A line parser recognizes what the design reference styles: headings, task items, list items, image lines, and the inline marks for bold, italic, code, and links. Marks get `.inkFaint`; headings the scaled sizes; a done task's text `.ink2` with a strikethrough. The gaps the design gives a marker, 12 for its column and 10 after it, are set with a kern on the space that follows it, so the text after a `-` starts where the design has it whatever the glyph measures.
- A task's checkbox and an image's thumbnail are drawn by subclasses of `NSTextLayoutFragment`, which the layout manager's delegate returns for a paragraph that carries the decoration attribute, so they live in the layout and scroll with the text. An `NSTextAttachment` would need its own character in the string, which the file does not have. The brackets of a task stay in the text, clear and kerned to the width of the box, which the fragment draws over them; the thumbnail sits in the fragment's bottom margin under the image line with the file's name as its caption. Until phase 3 the thumbnail is its frame alone, since the file is not on the device; the attachment folder of the note fills it then.
- The raw text of an image line and the brackets and address of a link are shown only on the paragraph that holds the caret. Elsewhere the styler gives them a font too small to have a width or a height and the clear color, so the characters stay in the string and the file while the line lays out as if they were not there, and an image line off the caret is its thumbnail alone. The paragraph being laid out learns whether it holds the caret from the view's selection, and on each selection change the coordinator tells the storage that the attributes of the paragraph the caret left and of the one it entered were edited, which makes the content storage ask for those two paragraphs again. A tap on the thumbnail puts the caret on its line, which reveals the raw line.
- Return inside a list inserts the next marker; Return on an empty item removes the marker. The accessory bar's buttons insert the marks at the selection. Command-B, Command-I, and Command-K do the same on macOS through the Format menu.
- Saving as typed: the view reports each change to `AppModel`, which writes the device copy at once and sends one commit on close, on selecting another note, on going to the background, or after thirty seconds without typing, as ux-redesign.md decides.

## What a phase leaves behind

At the end of a phase, the renders in `docs/design/` and the screenshots of the build agree, the previews cover the new components, `Localizable.xcstrings` holds every new string in both languages, and `docs/design-reference.md` has been corrected wherever the build taught something the reference had wrong.
